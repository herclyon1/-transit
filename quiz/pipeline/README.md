# 东亚地图数据管线（OSM 源）

把东亚地图的几何从"多个已简化的衍生数据集拼凑"换成"单一 OSM 原始数据"。
这份 README 记录**为什么每一步必须这么做**，避免以后有人（包括我自己）图省事抄近路。

## 背景：旧方案错在哪

旧数据的四个图层来自四个来源——国界/海岸线用 CGAZ、省界用 DataV、河流另有来源。
每一份都被各自独立简化过。现实里中朝国界和鸭绿江是同一条线，但在旧数据里它们是
两条来源不同、各自被削过的线，**永远不可能重合**。海南、中蒙边界是同样的病。

这类问题加密顶点治不好——加密只是让两条错开的线都变细腻，它们还是错开的。

## 为什么 OSM 能治

OSM 的边界是 relation 引用 way。中朝国界的 201 条 way 里，**123 条同时带着
`boundary=administrative` 和河流名**（鸭绿江/图们江）。国界和江在数据里就是同一个
对象，不存在对不上的可能。实测中位段长 76m（旧数据 t2 层是 472m）。

## 步骤

### 1. `dl.sh` — 下载 Geofabrik 提取包
21 个国家/地区，约 15GB。覆盖范围对应旧数据的 27 个 grp。

### 2. `filter.sh` — 按标签瘦身
只保留边界/海岸线/水体/河流及其引用对象。15GB → 数百 MB。

注意：输出文件名的临时后缀必须是 `xxx.part.pbf` 而不是 `xxx.pbf.part`，
否则 osmium 认不出格式，会静默失败。

### 3. `osmium merge filt/*.pbf -o ea_all.pbf` — **合并（关键步骤，不能跳过）**

> **必须先合并再组装关系。**
>
> Geofabrik 按国家切包时会切断跨境的边界关系。实测：朝鲜平安北道有 65 条成员 way，
> 其中 2 条只存在于中国包里。单独处理朝鲜包时，GDAL 只会打一句
> `Non closed ring detected` 的 warning，然后**静默丢掉这个省**。
>
> 也就是说按国家逐个处理，**每一条国境线上都可能掉单元且不报错**。
> 这是本项目历史上最典型的失败模式：不崩溃、只是少一块。

### 4. `extract.sh` — 组装行政区多边形
在合并文件上跑 `ogr2ogr ... multipolygons`。GDAL 的 OSM 驱动能处理 `type=boundary`。

### 5. 海岸线裁剪 — **必做**

OSM 的行政区边界走的是**领海线，不是海岸线**（国界关系 280 条成员 way 里只有 1 条
是海岸线）。不裁剪的话行政区会泡在海里——这才是"海南看着不对"的真正成因，
跟精度无关。

用 OSM 官方每日构建的陆地多边形裁剪：
<https://osmdata.openstreetmap.de/download/land-polygons-split-4326.zip>

必须用 **split 版**。complete 版里整个欧亚大陆是一个多边形（上千万顶点），
拿一个省去求交会慢到不可用。

裁剪正确性的判据：**内陆行政区面积必须分毫未变，只有沿海的会缩小。**
朝鲜实测——两江道/慈江道/黄海北道/平壤 数值完全不变，沿海各道缩小后与公开面积吻合
（开城 1301 对 1309、江原道 11081 对 11090）。

### 6. 名称与分组继承
几何取 OSM（权威），中文名和 grp 从旧的 612 单元按质心归属继承。
这样既拿到真实边界，又不丢已经整理好的中文标注。

### 7. 切瓦片

> **tippecanoe 按缩放级别做的简化，跟当初 mapshaper `interval` 毁掉精度是同一类陷阱。**
> `interval` 是面积阈值不是段长阈值，当年就是误解了这一点把国界削到 1469m。
> 切完必须逐级验证边界与河流/海岸线的对齐，不能切完就当完事。

## 验收红线

1. **单元数必须对得上 612**，少一个都要查到原因（平安北道就是这么抓出来的）
2. **内陆行政区裁剪前后面积不变**，变了说明裁剪逻辑有 bug
3. **边界段长中位数** 不得劣化到 200m 以上
4. 争议地区按实际控制归属，另出虚线范围 + 标注
